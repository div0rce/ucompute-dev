## 1. One-page summary

### What works today (verified, on named hardware only)

1. **UCompute Run: local AI inference.** A small open model in GGUF format runs on the computer itself through a pinned llama.cpp engine (release b11609). It streams output, can be cancelled, checks that a model fits in memory before loading it, verifies every download against a pinned SHA-256 hash and offers a local OpenAI-compatible API. All of this is verified on one Apple M2 MacBook Air running macOS 26.2. A Windows 11 laptop (Intel Arc 140V GPU) and a second Mac (Apple M2 Pro; that platform remains PLANNED per §27.1) have also run it.
2. **UCompute Mesh: private remote execution between your own paired devices.** Two devices on one local network pair with a short code and can then send a whole request to run on the other device. On a network that passes local discovery (a home network or phone hotspot) they find each other; on one that does not (campus Wi-Fi) they pair and reconnect by address. The connection is encrypted and both ends authenticate. Verified between a Mac and a Windows laptop through the daemons, most recently on 2026-10-22 with pairing in both directions. Through the apps' windows: the 2026-10-19 demonstration (section 3.2) and, on 2026-10-22, the Windows firewall consent step and pairing started in the Windows app, both done by hand. UI pairing (F-10-05) remains IMPLEMENTED_UNVERIFIED.
3. **Safe defaults.** By default no inference request leaves the device. Another device can receive work only after the user pairs it and allows it. A revoked device was cut off within a tenth of a second in three two-machine runs, and in tests and in the four two-machine runs that checked it (two on 2026-10-18, one on the 2026-10-19 hotspot, one on 2026-10-22), audit logs contained no prompt or response text.

### What does not exist (never imply it does)

| Distinction | What exists | What does **not** exist |
|---|---|---|
| Remote inference vs. pooling | Whole-request remote execution (spec Mode B). Each request runs entirely on one device the user picks | Splitting or partitioning one model across devices, pooling memory or GPUs, running a model too big for any single device. Pooling is not implemented or verified (Gate D; F-03-* NOT_STARTED) |
| Private Mesh vs. public Swarm | A private Mesh of devices the user paired, on one local network | An open or public network, contributing to strangers, a public relay, connections across the internet (Swarm/Mode F disabled; F-02-06 NAT traversal and relay NOT_STARTED; Gate F not verified) |
| Planned credits vs. billing | A binding design principle for future compute credits (D-019, spec §26.5) | Credits, earning, purchases, prices, fees, billing, payments, payouts, trusted-access allowlists, sharing modes. U-05 and F-07-01..11 are NOT_STARTED; F-07-12 (token-incentive feasibility) is IN_PROGRESS as research only. No §26.5 stage is authorized |
| Development builds vs. releases | Development builds: macOS ad-hoc signed and not notarized, Windows without a code-signing certificate. The project installed them on its 3 test machines | Any public release, download, signed or notarized installer, auto-update or alpha/beta cohort (B-007, B-008; Gate G incomplete; §31: no cohort started) |
| Protocol aspiration vs. interoperability | One implementation's peer protocol, EXPERIMENTAL. A local HTTP API that the official OpenAI client libraries work against | A second, independent implementation of the peer protocol, a stable protocol version, independently verified interoperability (U-01 NOT_STARTED; B-018) |

### Coverage at a glance

- **Three physical machines in total:** an Apple M2 MacBook Air (macOS 26.2), an Apple M2 Pro MacBook Pro (macOS 15.7.9) and an HP laptop with an Intel Core Ultra 7 258V and Arc 140V (Windows 11 Home 26200).
- **No platform is SUPPORTED** (spec §27.1). macOS 26.2 on Apple M2 and Windows 11 x64 on a Core Ultra 7 258V with Arc 140V are EXPERIMENTAL. Other Apple Silicon, including the M2 Pro on macOS 15.7.9, is PLANNED, as are Linux, NVIDIA/AMD GPUs, Intel Macs, mobile and browsers.
- **No throughput figure is a performance measure.** Every tokens-per-second number below comes from tiny models (stories15M, SmolLM2 360M, Qwen2.5 0.5B) and is a *path check*: it shows that the path works, not how fast it is.
- **What changed since the 2026-10-22 snapshot (1004b3b):** the Windows firewall consent step and pairing started on Windows now work on real hardware (by hand, 593d4ea Windows build, 40f78bd); connect at address and a remote run work on a network with no local discovery (18d5361); a full Mac–Windows daemon API run with the builds from before the fix rounds passed its mesh steps and exposed one product defect, a Sharing change ending a Disconnect hold (11ec77b); and three fix rounds (3df9438, 75a0a89, 18c4cf3, documented in 3a8f0d7 and 140eee9) fixed that defect and others in code, with unit, synthetic and SINGLE-HOST tests only.

- **What the site can use now:** sections 8 and 9. They rest only on evidence committed by 11ec77b, except the relayed live-page exception in claim 14, which is pending its record and not usable. Pending runs can add claims or remove section 9 rows. They withdraw a section 8 claim only if a retest shows a regression, and a new snapshot would say so.

| **Current implementation** | Code exists; acceptance is incomplete |
| **Committed engineering scope** | In the ledger or backlog; not implemented |

Platform support uses only the spec §27.1 terms: SUPPORTED (passed a stable release gate; **none yet**), EXPERIMENTAL, PLANNED and UNSUPPORTED. A claim can be Verified reality while its platform is EXPERIMENTAL: the label describes the evidence, the support term describes the platform.

The "Evidence scope" column in the tables uses these terms:

- **TWO-MACHINE**: two different physical computers.
- **REAL**: one physical machine with the real engine.

### 4.2 Behaviour changes in the fix rounds (3df9438; unit and SINGLE-HOST only)

- **Refusals before the other device has proved its key.** Since round 3, a refusal reached before the other device has proved its key on the control stream reads `peer_unauthorized` ("did not prove it is <name>"), and the dial goes on to the next address. So a device that was revoked by its peer **no longer reads `peer_revoked` on a new dial**; it reads `peer_unauthorized`. Reason: on the network path such a refusal can be forged, so it is not trusted as the device's own verdict (ADR-0003 §9.3). The 2026-10-18/19/22 revocation results in section 3.2 were made with earlier builds that read `peer_revoked`; the claim that the next request is refused is unchanged.
- **Disconnect hold.** A hold now survives a Sharing change and ends with Connect, unpair, revoke, a peer's revocation of the held device, networking off and on, or a service restart.
- **Protocol minor 1.** Revocations now cross a hold: each time the held device dials, the two exchange the revocations due before the close, so delivery waits for the held device's next redial (backoff at most 300 s). No message or field was added. Older builds interoperate: the two devices negotiate the lower minor (F-08-10, SINGLE-HOST). A held minor-0 peer gets the old close (`CLOSE_HELD`) with no exchange; a minor-1 device held by a minor-0 build reads `peer_unauthorized`, not `peer_held`. Every installed build so far (Mac d9d8067, Windows 593d4ea and older) is minor 0. Known limit: two devices that hold each other exchange nothing until one connects.

## 6. Known limitations

- **Hardware and OS coverage.** Three machines: Apple M2 on macOS 26.2, Apple M2 Pro on macOS 15.7.9, and Intel Arc 140V on Windows 11 Home 26200. There is no Linux host (B-004) and no mobile device (B-003). There are no NVIDIA, AMD or Intel Mac results. The Mac-M2Pro evidence covers the packaged app and a partial Mesh run only. No platform is SUPPORTED.
- **Small models only.** The development Mac has 8 GB (B-010). Inference evidence uses stories15M, stories260K, SmolLM2 360M and Qwen2.5 0.5B; the largest model measured, for memory planning only, is Qwen2.5 1.5B q4_k_m. Memory estimates are calibrated for llama.cpp b11609 on Apple Silicon.
- **One local network.** Mesh evidence covers two devices on the same Wi-Fi network or phone hotspot. There is no relay, no NAT traversal and no path across the internet (F-02-06 NOT_STARTED).
- **Internet on first run.** The engine and models are downloaded on first use. With networking switched on (off by default), a device announces itself on the local network for discovery and pairing. Operation with no internet is untested (X-20 NOT_STARTED).
- **Networks that drop multicast.** On eduroam, automatic discovery fails because the network does not pass mDNS between clients. Pairing, connect at address and remote execution still work there (2026-10-18 and 2026-10-22). Discovery was verified on a phone hotspot.
- **Windows Firewall.** The app's consent step adds a rule for Private networks only, so the laptop's network profile must be Private (the owner set it). The consent step and pairing started on Windows work with the 593d4ea build (2026-10-22). The later change to how the app reads its rule (75a0a89) has not run on Windows.
- **macOS firewall (suspected).** One Mac-to-Mac pairing failure on 2026-10-21 may come from the macOS application firewall blocking a newly built, ad-hoc-signed app. The cause is not established.
- **Unsigned or ad-hoc builds.** macOS builds are ad-hoc signed and not notarized, so `spctl` rejects them and a downloaded copy needs "Open Anyway" once. Windows builds carry no code-signing certificate (B-008).
- **No public release.** There is no binary download, no WP-08 release record, no executed CI pipeline, no alpha or beta cohort and no published source (B-007, Gate G, §31).
- **Fixture numbers are path checks.** stories15M tok/s figures say nothing about real-model performance: the 15M fixture even runs faster on CPU than on Metal. The fixture's weight license is unverified, so it is never redistributed (B-011). The 0.5B and 360M numbers come from 3 runs on one machine, not a controlled study.
- **Builds behind the evidence differ from the code.** Every physical run so far used builds from before the fix rounds (Mac d9d8067; Windows 593d4ea and caf1497). The fixes in 3df9438, 75a0a89 and 18c4cf3 have only unit, synthetic and SINGLE-HOST evidence. The 2026-10-22 runs drove the apps' daemons through their APIs, except the firewall step and pairing started on Windows, which were done by hand.
- **Test hosts sleep or go offline.** The tester's Mac slept twice during the 2026-10-21 run; the laptop's battery died at 22:05 UTC on 2026-10-22, ending that run's session (11ec77b). The Mac slept repeatedly during the 2026-10-23 SINGLE-HOST shakedown (verdicts stand; timings count awake time only). Nothing has been tested about the product's own behaviour across sleep and wake.
- **Load-sensitive results.** Tests on Mac-M2 often run at high load from other processes. One latency bound (F-06-04) fails there and passed on a quiet Mac-M2Pro; since 2026-10-23 its cause is undetermined.
- **Transport privacy only.** Encryption protects traffic between paired devices. The device that runs a request necessarily processes the prompt, so there is no confidential-computing or provider-blind execution (F-06-11 research only). The packet-capture proof is SINGLE-HOST; no LAN capture was taken.
- **Windows key-file protection.** The identity files on Windows inherit the profile folder's access rights; the product sets none of its own, and a second account's access is untested (B-017).
- **Accessibility.** No screen reader has been run against an installed app on either OS; the evidence is automated checks and accessibility-tree dumps.
